# F06-nested-copy-offsets - a copybook that COPYs another: the copybook's own layout ignores the nested bytes (the program's view is right)

R06OUTER copies R06INNER (25 bytes) inside its ADDRESS group, so R06-AFTER starts at byte 35. Truth: offset 35 in `layout R06OUTER` and `field R06-AFTER`. Tool: offset 10 (the nested bytes are not counted) while the program's own view (`layout R06-RECORD --program R06PGM`) says 35. Test data and sort-card overlaps built from `layout` are wrong for every field after a nested COPY.

Fixed by ROADMAP re-parse item 27 (LESSONS 214): the copybook's own layout is computed with its nested COPY put in place by the resolver the programs use, so R06-AFTER is at 35 in `layout R06OUTER` and `field R06-AFTER`, and R06-ADDRESS is a 25-byte group. R06OUTER's rows are its own items only - R06-INNER-A and R06-INNER-B are R06INNER's rows, cited there - and `layout R06OUTER` says under its table that COPY R06INNER at line 3 is counted in the offsets and its items are R06INNER's own. A nested COPY whose text is not in the layout (not found, skipped, IBM-supplied) is a 'layout_warning' on the copybook. The program's view (check 2) was right before and is a control: verify.py prints it FIXED.
