Mainframe Atlas Field Manual

A deterministic fact index over a COBOL / JCL / IMS / DB2 / VSAM estate, so a language model answers from rows it can cite instead of text it half-remembers.

Why a parser, not a model

Indexing a large mainframe folder and chatting with it hallucinates, and not because the folder is big. Four things are going wrong at once:

  • Training on the estate stores style, not facts. The model learns the shop's naming grammar and then emits perfectly plausible program names, field names and job flows that do not exist.
  • Embeddings collapse on cryptic identifiers. WS-PLCY-STAT-CD-01 and WS-PLCY-STAT-CD-02 are the same point in vector space; thousands of near-identical CRUD paragraphs cluster together; the retriever returns the wrong-but-similar member and the model reasons fluently about it.
  • Silent zero recall. When nothing relevant is retrieved, the model fills the gap from memory rather than saying "not found". That is the hallucination mechanism.
  • The facts are not in the text. What a job does lives in control cards, PROC symbolics, IKJEFT01's SYSTSIN, DFSRRC00's PARM, GDG relative generations, PCB order, COPY … REPLACING and the scheduler. No chunk of COBOL contains them.

So Atlas is a parser. It walks the folder, extracts hard facts into SQLite with a line citation on every row, records everything it could not resolve, and hands the model a small fact pack. The model is a reader that cites; a mechanical gate rejects any answer whose citations do not check out.

Getting the code from the mainframe

The index is built from a folder, so something has to fill that folder correctly and repeatably. sources.json answers "where does the automation look": each row maps a mainframe dataset to a local folder (PDS) or file (sequential), a kind, a system, and whether it is the production copy. Zowe CLI does the download; the manifest the build needs is generated from the same file, so the two cannot disagree.

python -m atlas.ui --config sources.json                  # desktop UI (Tkinter - nothing to install)

python -m atlas.fetch --config sources.json --init        # or the command line: starter config
python -m atlas.fetch --config sources.json --check       # zowe on PATH? profile works?
python -m atlas.fetch --config sources.json --plan        # print every zowe command, run nothing
python -m atlas.fetch --config sources.json --all --build # download everything, then re-index

Several departments, each with its own libraries

Every source row carries a system (the department), and that one field drives the rest. Each department gets its own folder under the root (C:\estate\CLAIMS\PROD.CLAIMS.SRC), so same-named members never collide on disk. Bulk add takes a pasted dataset list and infers kinds from the names (SRC, COPYLIB, JCLLIB, PROCLIB, PARMLIB, PSBSOURCE, DBDSRC, BMS, MFS, CSD, STAGE1…); compiled libraries (PSBLIB, DBDLIB, ACBLIB, LOADLIB) are added disabled with a warning — nothing to parse. The System filter and Fetch system work on one department at a time.

The part that matters for correctness: a CLAIMS program that says COPY POLREC gets the CLAIMS copy, never POLICY's. Candidates are ranked COPY … OF lib › same department in its declared order › same department › authoritative › same folder › first found, and the choice is recorded in the ambiguous_copybook note either way. The declared order is the order of a department's copybook rows in the table (Move up / Move down) — the SYSLIB concatenation its programs compile against. dataset X names each writer's and reader's department and says Crosses departments when they differ; ambiguous shows which departments hold each duplicate name.

When zowe asks for a host, a user or a passwordIf your zowe command works in a window without a prompt, the toolkit needs no password either: it did not find the configuration your window uses. First, run the toolkit from the folder where your zowe command works, or set Run zowe from folder, and leave Zowe daemon off unticked; Check Zowe shows which configuration files it sees from that folder. The session password is optional and comes last — for a shop whose profile stores none, where zowe asks in the window too; run by the toolkit it cannot ask, so a fetch creates the folders and downloads nothing — the log says so. Either store it once in the profile (zowe config secure, kept in Windows Credential Manager) or give it for one session with the UI's Sign in or --ask-password on the command line: it reaches the zowe subprocess through its own ZOWE_OPT_PASSWORD variable and is never written to sources.json, the log or a crash file.
Shop-specific flagsA different profile type, an encoding, --preserve-original-letter-case: put them in extra_args (global or per source). That is a config edit, not a code change, and the log shows the exact command so it can be corrected on the spot. Include the routing exports as sources too — the CSD extract (kind csd) and the IMS stage-1 source (kind imsgen) — or "which transaction runs this" stays unknown.

Building the index

Copy manifest.example.json to manifest.json and list the production libraries — the index cannot otherwise know which of several same-named copies is real. Then:

python -m atlas.supervise  C:\estate  --db atlas.db  --manifest manifest.json  --also C:\docs
python -m atlas.query  --db atlas.db coverage        # read this FIRST
python -m atlas.query  --db atlas.db ambiguous       # duplicate member names

A few thousand members take minutes; a large estate takes hours, so run it under the watchdog (atlas.supervise takes exactly the build's arguments). Every ten seconds the build says how far it is, how long is left at the current rate, and which member is in hand with its size; a line when a folder or a kind is done; a member still in hand after 15 minutes is given up on and recorded. A build silent for three minutes (a parser frozen inside a regular expression) is killed by the watchdog, the member in hand is written to atlas-skip.txt, and the build restarts keeping everything parsed so far. Beside atlas.db you will find atlas-current.txt (the member in hand), atlas-skip.txt, atlas-problems.txt (every member or file that could not be indexed, one line each, listed again at the end of the build) and, after a crash, atlas-crash.txt.

Build or rebuildRun the same command every time. Without --rebuild only new and changed members are parsed, and a toolkit or manifest change re-parses everything by itself. With --rebuild the index is deleted and every member parsed from zero — for the very first build only. After a stop (Ctrl+C, a crash) continue without it. The watchdog never passes --rebuild to a restart, and it refuses to start when the command names fewer folders than the index holds — an --also left out once would remove every document from the index — unless you add --allow-prune because the folder really moved.

Every member that fails to parse is recorded with its error; every reference that could not be resolved becomes a row in unresolved. The coverage report is the list of question classes the index will answer wrong, not merely incompletely — fix the inputs it names (missing copybook libraries, no scheduler export, ambiguous copies) before trusting answers. It says what ok / partial / skipped / failed mean, names the members parsed only in part and why (usually a copybook the index does not have), keeps a program whose copybook was chosen among several same-named ones with different content in its own row — "Complete, with a copybook chosen among several": every COPY expanded, the ambiguous_copybook row names the copy used, and program reads complete (copybook chosen among several) although the index marks it partial until the next re-parse — names every member not indexed at all — including those given up on before a restart — and explains each unresolved kind: what it means and what closes it. coverage --all names every member instead of the first fifteen.

Documents and pictures

The documentation folder is not a mainframe dataset — it already sits on the laptop. Name it under Document folders in the UI (or extra_roots in sources.json, or --also DIR on the build) and it is indexed alongside the code: .docx / .xlsx / .pptx / .vsdx text, headings, tables and slide notes; .pdf best-effort; .txt / .md / .html. Legacy .doc / .xls / .ppt cannot be read directly: Prepare documents in the UI (or python -m atlas.convert <folder>) first extracts every .zip under the document folders — subfolders and zips inside zips included — into a <name>.unzipped folder beside the archive, then saves every one as .docx / .xlsx / .pptx beside the original, with the Office already on the laptop (nothing installed, nothing deleted); the build then reads the copy and skips the original.

Missing copybooks, rebuilt from the expanded programs. A program whose copybook is not in the estate is parsed only in part. When the estate holds the compiler listings (or expanded source), python -m atlas.recover --db atlas.db reads where each copied block starts and ends — a listing flags every copied line, and any expanded text is lined up against the original program, so the lines it adds at a COPY are the copybook even with no marks — checks every block before trusting it, and writes each missing copybook out under estate\SHARED\RECOVERED-COPYBOOKS, marked as recovered and naming the program it came from; the next build resolves every program that copies it, and when the real copybook arrives the recovered one goes. A copybook seen in several programs is compared across them; work\recover.md names every one and how it was chosen. The same run reads the listing of every program whose copybook the build chose among several same-named libraries — the listing's own table names the library the compiler read each copybook from — and checks each choice: confirmed, contradicted (a wrong fact, named in the report with the library the listing says) or unknown; coverage, program and copybook repeat what the listings say. The same rows give the fetch list: the report tables the library datasets named by the listings the run reads (those of the programs that copy a missing copybook, one the index holds only as a recovered copy, or one chosen among several; not every listing in the estate) — the copybooks to fetch for that came from each first, whether the index already holds it, how many programs. A copybook the build has read as a recovered copy is no longer missing, but its library stays on the list until the real member arrives; work etch-list.txt holds the not-fetched datasets one per line, datasets only, to paste into Bulk add or give to zowe; once fetched and built, those copybooks resolve and the recovered copies go.

PDFs, scanned or not. A PDF with real text is read directly; a scanned PDF — or one whose fonts defeat the text extractor — is handled by OCR images: its pages are rendered with the Windows PDF renderer (Windows.Data.Pdf, part of Windows 10/11, nothing to install) and read by the same OCR engine as the pictures, each page becoming a citable section 1001+ of that document. Nothing leaves the laptop and no model tokens are spent.

Pictures are read, not just counted. OCR images in the UI (or python -m atlas.ocr --db atlas.db --out out/images) pulls every image out of the documents — including the metafiles (EMF/WMF) that Word, Excel and Visio store a pasted diagram as, drawn onto a bitmap first because the engine cannot decode them, and every page of a multi-page TIFF — and runs the OCR engine that ships with Windows 10/11 — no install, no network, no model tokens. Pictures already read are skipped on the next run; converted copies go under out/images, never into your documents folder. The recognised text becomes a section of the document (image 1, image 2…), searchable and citable. Pictures OCR cannot read (hand-drawn diagrams, whiteboard photos) are listed with their extracted path: those few are worth a vision-model call, chosen by hand.

Recorded sessions are read too. A knowledge-transfer or outage walkthrough recording holds what nobody wrote down. Atlas: read recordings in VS Code (or python -m atlas.video C:\Recordings --out C:\docs\Video) reads every .mp4 / .m4v / .mov / .wmv / .avi under a folder with what Windows already has: a frame every ten seconds through the same OCR engine (a screen shown for a minute is written once, at the time it appeared; what the engine reads is checked against the index — a misread name is snapped to the real one, an unknown one is marked ?, a line with nothing recognisable is dropped — because a shared screen in a recording is small and blurred and the engine invents where it cannot read; a full-screen emulator in a 1080p recording reads mostly, a shared window in a 720p recording reads in fragments; --keep-frames saves a dozen frames with their text so you can see what it saw), and what was said from the meeting's own caption file beside the recording (.vtt or .srt, the transcript Teams or Stream makes — download it). It writes <name>.video.docx — one section per two minutes, every line stamped [00:12:05] SAID: or [00:12:10] SCREEN: — into --out, which must be one of the folders the build reads; then run your usual build command and it is document <NAME>.VIDEO, found by docs TERM. Without a caption file the speech is not transcribed and the transcript says so: the speech recogniser Windows ships reads synthetic speech well and real meetings badly — several voices, room noise, accents and mainframe words come back as fluent sentences nobody said — so it runs only on request (--speech-recogniser) and its lines are labelled unreliable. A caption file on its own is read too. Keep recordings and caption files outside the folders the build reads. Quote a transcript as "said in the recording at 00:12:05", never as fact.

Spreadsheets and tables are rows, not counts. A workbook's tab is a section whose text is its rows — row 12: TC-GEN-01 | Add gender N | PASS, with the sheet's own row numbers — so a QA results workbook is searched (docs TC-GEN-01), read (doc QAREL12 --sections 2) and cited ([[QAREL12 2 "TC-GEN-01"]]) tab by tab; a tab of thousands of rows is cut into parts between rows. Word and PowerPoint tables are rendered the same way inside their section. Every picture is anchored to where it sits — the tab, the slide, or the Word heading above it — and the OCR section's heading says so (image: image3.png (sheet: Gender Tests)); doc NAME lists the pictures by place, doc --list QA the indexed documents in a folder. The workbook is known by its file name without the extension.

Asking questions

Every command prints Markdown with a MEMBER:line citation on each row and ends with the unresolved items in its scope.

program NAMEDossier: where it runs (jobs, transactions, ENTRY aliases), what it calls and is called by, copybooks (with REPLACING), files joined through JCL to datasets with direction, DB2 tables, DL/I calls already resolved to database and PROCOPT through the PSB, CICS commands (maps, TRANSIDs, files, queues), MQ queues, structure (PERFORM, GO TO, fall-through), literals and message texts it sets, control cards it reads, documents mentioning it. job NAMEStep by step: the effective program (not PGM=), every EXEC PROC= expanded with this job's symbolics and overrides, control cards quoted — also DSN=LIB(MEMBER) cards — datasets in/out with the signal that decided direction, GDG generation, IF/ELSE and COND guards (runs only when), JOBLIB, JCLLIB, jobs it submits through INTRDR; temporaries hidden, symbols it cannot resolve listed as symbolic. field NAME [--all] [--program PGM]Every definition with offset and length, version skew across copies, programs including the copybooks, references by mode (write first), 88-level values, literals moved to it, sort cards overlapping its bytes, DL/I and SQL statements whose I/O area holds it. Before it, the fields the PROCEDURE DIVISION names and only those, with offsets; after it, the paragraphs nothing reaches. The loop with a model

The budget is small, so the model never reads the repository. It reads packs.

  1. python -m atlas.query --db atlas.db pack CLMPOST --budget 12000 > pack.md — a few hundred lines of facts and evidence lines, token estimate on the first line; --kind job for a job with its control cards, copybook, transaction or field likewise.
  2. The model answers using only the pack, citing each claim as [[MEMBER line "token"]]. What it cannot cite it marks UNVERIFIED or INSUFFICIENT EVIDENCE.
  3. python -m atlas.verify_citations answer.md --db atlas.db — opens each cited member, checks the quoted token is on those lines, warns when the line is a comment, and rejects the answer on any failure.
  4. cite MEMBER a-b fetches more lines only when the pack was not enough.

In VS Code

The same loop from the editor. Open the toolkit folder as the workspace — git pull brings the tasks and the prompts with it. Terminal → Run Task → Atlas: pack NAME writes work/pack.md (with --out, never the shell's >: PowerShell 5.1 writes UTF-16 and the model reads garbage). In Copilot Chat type /atlas-answer — the prompt attaches the pack and carries the rules. Save the answer as work/answer.md; Run Task → Atlas: verify; on FAIL, /atlas-fix returns the corrected answer. One prompt per playbook: /atlas-program (what a program does, from walk), /atlas-impact, /atlas-job, /atlas-trace, /atlas-populate, /atlas-abend, /atlas-values, /atlas-tests, /atlas-design. .github/copilot-instructions.md is the contract Copilot loads by itself; for another chat tool the same requests are text in templates/REQUESTS.md. The packs carry real source lines — that is fine for the company's model on the company laptop; nothing under work/ travels home. Details: docs/VSCODE.md.

A typical analysis question is one model call over roughly 2–5k tokens of input. Indexing, impact sets, dossiers and test-condition inventories cost nothing. The model list at work is mixed-vendor; the design does not depend on which one is used — bulk work is free, the gate makes the model's choice matter less, and the strongest available model is reserved for design and verification.

Rules the model follows

These live in templates/CLAUDE.md; copy that file to the estate root next to atlas.db.

  • The index knows this estate; the model does not. Run the matching query before answering. A fact from neither the index nor an opened line is UNKNOWN.
  • Cite or abstain. Every claim carries [[MEMBER line "token"]]; the token is quoted, never paraphrased. Run the gate before delivering.
  • FACTS, then INFERENCE, then UNRESOLVED IN SCOPE, then NOT SEARCHED. Never mixed.
  • A missing row is not "no link". No caller found ≠ no caller; dynamic CALLs, unindexed source, online transactions and the scheduler can all reach it.
  • DISP is not direction. PGM= is not the program. PCB arguments are positional. Use mode_source, effective_pgm, and the PSB order.
  • Same member name ≠ same program; same copybook ≠ same layout across systems. Check ambiguous and version skew.
  • Group-level MOVEs, READ INTO, WRITE FROM, INITIALIZE and CALL BY REFERENCE touch fields without naming them. Follow parents and USING positions.
  • A never-PERFORMed paragraph may still run (fall-through, GO TO, SORT procedures), and a program with no caller may be started by a transaction, an INTRDR submit or the scheduler. Never call code dead without saying which caveats were not checked.
  • Documents describe intent; code describes behaviour. Quote both when they disagree and say they disagree.
  • Generated code takes field names from field, offsets from layout, style from a real exemplar, and ends with a HUMAN MUST VERIFY list.

What it does not do

ROADMAP.md in the toolkit carries the full coverage matrix — every artefact type and question class marked facts, text or no — and the ordered list of what is not built yet (RM-01 … RM-13). The short version:

  • It is not a compiler. Grammar-aware, conservative extraction over properly tokenised source, reporting what it skipped. A compiler listing (LIST/MAP/XREF) is the authoritative expanded source — listings are classified and searchable but not yet parsed (RM-01), so an abend offset cannot be mapped to a statement.
  • It is not a scheduler. Export CA-7 / Control-M / TWS / Zeke to CSV and load with --sched; native exports need a loader (RM-07 — twenty lines of the export with the names changed is enough to build one). Jobs submitted through INTRDR are linked already. Until a scheduler is loaded, "dead job" and "what runs before" are unanswerable, and the reports say so.
  • Transaction routing needs the exports. The CICS CSD (DFHCSDUP DEFINE deck or LIST report, also when embedded in a JCL SYSIN) and the IMS stage-1 (APPLCTN/TRANSACT) are parsed; if those exports are not in the folder, "which transaction runs this" is unknown and coverage says so. Transactions reached only from code (START / RETURN TRANSID / CHNG) are shown as such. IMS program names are assumed equal to PSB names unless GPSB= was used — recorded on every such row.
  • Non-COBOL code contributes no facts. Easytrieve, Assembler, PL/I, REXX, CLIST and SAS members are classified and searchable; an impact chain through them ends at "NOT in index" (RM-05). Easytrieve and SAS steps do yield their files and fields from the JCL.
  • DB2 DDL, BIND cards and catalog unloads are not parsed (RM-02): views are not resolved to base tables, CHECK constraints do not feed values, and a program's plan is known only where the CSD names it.
  • One level short in IMS and MFS (RM-03): a DL/I call is tied to its database and PROCOPT, not yet to the segment its SSA names; an MFS field is not yet joined to the program's I/O-area field.
  • Not modelled: SYNC alignment slack, dynamic SQL targets, CALL targets read from control tables or arriving in LINKAGE, symbol substitution inside instream data, nested COBOL programs and COPY inside a copybook (RM-08), link-edit aliases and the compile PROC's SYSLIB order (RM-06), DCB/LRECL on the DD, MQSC queue definitions. All appear as unresolved or are named by coverage; a DSN still containing & after expansion is listed as symbolic, never guessed.
  • One rule to confirm on your system. When a PROC statement gives a symbol a default and an instream SET gives it another, the index assumes the PROC default wins (EXEC override › PROC default › SET). Check it once against a real job's JESJCL; if your system disagrees, flip PROC_DEFAULT_BEATS_SET in atlas/jcl.py and rebuild — nothing else changes.

The four names

PDS member name, PROGRAM-ID, CSECT and load module or alias routinely differ. Atlas keys members by path, stores PROGRAM-ID separately, hashes columns 8–72 (norm_sha) to find true duplicates, and never merges by name.

Citation syntax

[[CLMPOST 412 "CALL 'RATECALC'"]]                 one line
[[CLMPOST:412 "CALL 'RATECALC'"]]                 the form the reports print — also accepted
[[CLMNIGHT 17-19 "RUN PROGRAM(PREMCALC)"]]        a range (wider than 20 lines is a WARN)
[[CLMPOST(jcl) 3 "PGM=CLMPOST"]]                  a kind, when a PSB or a job shares the name
[[POLICY/DUPREC 1 "PIC X(9)"]]                    a department, when two own different copies
[[libs/copy/PMASTREC.cpy 11 "COMP-3"]]            a path
[[CLAIMSPEC 3 "retention period"]]                a document section (OCR'd images are 1001+)
[[CLAIMS PLAN V1.2 3 "retention period"]]         a document named with spaces and dots - exactly as the report prints it
[[KT-SESSION.VIDEO 4 "CLMPOST"]]                  a recording's transcript (prose, never fact)

The token must literally appear on the cited line(s). The gate checks case-insensitively with whitespace collapsed; a token under 6 characters is a WARN, a cited line that is a comment is a WARN, a member that changed since the index was built is a FAIL (run the build again — not from empty — and cite again); a [[...]] the gate cannot read is a FAIL; it also lists assertive lines that carry no citation.
