# Scenario audit - what a real month of analysis asks, and what the tool answers (2026-09-21)

His question: 'This is only one example I asked. There could be many scenarios this tool should handle but was not built for.' True. This audit lists the scenarios a senior insurance mainframe developer runs in a month and checks each against the tool as it is: full / partial / none, with the command and the code line. The ranked table first (partial and none only), the full audit after it.

## Honest note

The tool was built around finding things: every command answers "where is this name, who names it, which job/dataset/table touches it", and every join is by a name (field, DD, DSN, table, transaction, PCB position) or by fixed bytes (sort card, file record twin). Impact analysis asks a different question: it follows a value across renames (MOVE A TO B, CALL USING into a LINKAGE name, WRITE FROM into a record that the next program reads under another copybook), it needs order in time (which write is live at the CALL, which job ran before this one, what step 3 sees after step 2), and it needs a judgement of overlap (bytes under another name through REDEFINES or a group MOVE, truncation at the landing field, an 88 value set that the reader does not know). I stored one row per name per line and never the pair, so the moment a program does `MOVE PM-POLICY-STATUS TO WS-STAT` the estate loses the thread; that MOVE is the normal way COBOL passes anything anywhere, and I should have designed the fact for it on day one instead of the caveat sentence `field` prints. The same blind spot shows up as a wrong fact in the current index: `ADD A B GIVING C` never records C as written. Your MOVE example is one instance of three whole families (value, time, overlap) that the gap table lists row by row; the batch item closes the first family and labels where it stops, the other two remain roadmap work.

## The honest one-line answer to "what were you expecting that you did not consider"

The tool was built **artefact by artefact** (a dossier per program, job, dataset, copybook, field, table, DBD, screen, transaction) and every join is by **NAME** (field name, DD name, DSN, table, PCB position, BMS symbolic name) or by **BYTES** (sort-card position, file-record twin). Three families of question that a change-impact or incident analysis needs were never built, because none of them joins by name or bytes:

1. **By VALUE through renames** - `MOVE A TO B`, group moves, REDEFINES, CALL USING/LINKAGE, WRITE FROM/READ INTO, INSERT/SELECT, ISRT/GU: "where does this value end up" and "where did this bad value come from". `field_ref` stores one row per name with a mode (schema.sql:169-176); `MOVE A TO B` becomes an unrelated `read A` and `write B` (cobol.py:1547-1548). `diff` itself says it: "no fact the index tracks changed: the edit is inside statements (a condition, a MOVE, a literal...)" (query.py:3411-3413).
2. **By TIME** - schedule order, what ran before, restart from step n, which generation to restore. Only one-hop `sched_dep` rows from a CSV (build.py:1028-1073, schema.sql:663-668) and INTRDR edges (build.py:1656-1658); ROADMAP RM-04 (ROADMAP.md:103-107) is not built.
3. **By OFFSET** - abend offset to statement (compiler listing, RM-01, ROADMAP.md:89-93).

The plan for family 1 is below (part 1); the full scenario audit is part 2.

## Part 1 - Plan: value flow (`data_flow` edges) for ROADMAP "Next re-parse batch", item 14

**Fact missing today.** No table records that the value of one item reaches another. `flow_from` (query.py:773-862) already follows three cross-program routes (CALL USING position -> callee LINKAGE, LINKAGE back to callers, same bytes of a file record read elsewhere) but it is called only from `literal` (query.py:1108), starts only at a literal's first MOVE target (query.py:1098), and cannot cross a single in-program `MOVE`. `field` prints a caveat instead (query.py:968-969); `column` stops at "set by MOVE @line" (query.py:2184-2190); `pair` and `conditions` exclude group moves (query.py:2555-2556, 3037-3038).

Proof on the scratch estate (PGMA reads PMASTREC, `MOVE PM-POLICY-STATUS TO WS-STAT`, `MOVE WS-STAT TO OUT-STATUS`, WRITE to PROD.POLICY.OUT, `CALL 'PGMB' USING WS-STAT`; PGMB `MOVE LK-STAT TO WS-X`, `IF WS-X = 'AC'`, INSERT INTO AUDIT_TBL; PGMC reads PROD.POLICY.OUT as IN-STATUS): `field PM-POLICY-STATUS` shows only "read PGMA MOVE x1 @PGMA:27"; `field WS-STAT` shows write/read rows and no destination; `literal AC` says "no CALL/LINKAGE/file route found"; `column AUDIT_TBL.STATUS_CD` says "set by MOVE @PGMB:13" and nothing before it. None of PGMB.WS-X, PGMC.IN-STATUS or PROD.POLICY.OUT bytes 13-14 is reachable from the field.

**Parser (atlas/cobol.py - a FACT_MODULES file, build.py:480; forces the overnight re-parse, so it ships in the batch, ROADMAP.md:127-131).** Add `flows: List[(src, src_kind, dst, dst_kind, verb, pos, partial, corr, ln)]` to `ProgramFacts` beside `field_refs` (cobol.py:277) and emit from the existing verb dispatch (cobol.py:1539-1671):
- `MOVE` (1541-1551): one edge per (source identifier, each target); literal source -> `src_kind='literal'` (keep `literal_ref` as is); `CORRESPONDING` sets `corr=1` (pairing by child name is done at query time from `field.parent_id`).
- `COMPUTE`/`ADD`/`SUBTRACT`/`MULTIPLY`/`DIVIDE` (1553-1572): operand -> target/GIVING/REMAINDER edges, verb kept (derivation, not a copy - the report must say so).
- `STRING`/`UNSTRING` (1574-1589): sources -> INTO target; `SET` (1595-1599); `INSPECT ... TALLYING` (1623-1625).
- `READ f INTO x` / `RETURN ... INTO` (1606-1609): `fd_record -> x`; `WRITE/REWRITE/RELEASE rec FROM y` (1611-1614): `y -> rec`. These are the hops that make the file route work for records built in WORKING-STORAGE.
- `CALL ... USING` (1637-1641): `arg -> CALL:<target>#<pos>` with `pos` (resolution to the callee's LINKAGE stays a query-time join on `call_edge.using_args` + `program.linkage_using`, schema.sql:71, 111).
- Reference modification `X(1:2)` and subscripts: keep the base name, set `partial=1`.
- Already sufficient, no change: DB2 host var <-> column (`sql_col_ref`, cobol.py:897-931, schema.sql:245-256); DL/I I/O area (`dli_call.io_area`, schema.sql:359).
- One more column for CICS/MQ hops: `cics_cmd.host_field` (schema.sql:582-590 has none; the host fields are already read in `_exec_refs`, cobol.py:1493-1516) so READQ/WRITEQ TS/TD, GET/PUT CONTAINER, RETRIEVE and MQGET/MQPUT buffers become edges into and out of a named resource.

**Schema (atlas/schema.sql, after `field_ref` at line 176).** `data_flow(id, program_id REFERENCES program ON DELETE CASCADE, src TEXT, src_kind TEXT /*field|literal|file_record|call_arg*/, dst TEXT, dst_kind TEXT, verb TEXT, pos INTEGER, partial INTEGER DEFAULT 0, corr INTEGER DEFAULT 0, line INTEGER)` with indexes on `src` and `dst`; `ALTER cics_cmd ADD host_field TEXT`. **Store (atlas/build.py:1391)** one `executemany` beside `field_ref`; `cics_cmd` insert at build.py:1331 gains the column. Size: about one row per operand pair of a data-moving statement, i.e. at most ~1.5x today's `write` field_refs.

**Query (atlas/query.py - no re-parse cost, ships with the batch).**
- New command `flow FIELD [--program PGM] [--depth N] [--back] [--budget CHARS]`: BFS over `data_flow` inside a program, and at each node:
  (a) **group containment**: a group destination fans out to its children (`field.parent_id`, schema.sql:136); a group source maps each child onto the destination's twin fields by byte overlap (offsets already computed, schema.sql:149-150; the twin query pattern exists at query.py:846-851) - this is the "group MOVE" answer;
  (b) **REDEFINES**: items sharing bytes under the same 01 (`field.redefines`, schema.sql:147, plus offset overlap) are printed as `aliases bytes x-y`;
  (c) **cross-program hops**, all from existing tables: CALL USING pos -> callee `linkage_using[pos]` (reuse query.py:781-805); LINK/XCTL COMMAREA -> the callee's `DFHCOMMAREA` 01 looked up by name (CICS programs have empty `linkage_using` because cobol.py:344 fills it only from PROCEDURE DIVISION USING; the COMMAREA argument is already stored, cobol.py:1019-1030); LINKAGE back to callers (query.py:807-822); file: `fd_record -> file_decl.assign_dd -> dd.dsn_resolved -> reader programs' fd_record` twins by byte range (generalise query.py:824-861 from one field to a range); DB2: `sql_col_ref` write host_var -> (tbl,col) -> every `sql_col_ref` read host_var estate-wide; IMS: ISRT/REPL `io_area` + `dbd_name` -> GU/GN `io_area` on the same `dbd_name` in any program (segment-exact only after RM-03, ROADMAP.md:100-102); CICS TS/TD/container and MQ through `cics_cmd.host_field` / `interface_edge`.
  Output: one row per hop - kind (`MOVE`, `group MOVE bytes 13-14`, `CALL PGMB arg 1`, `WRITE -> PROD.POLICY.OUT -> READ PGMC bytes 13-14`, `INSERT AUDIT_TBL.STATUS_CD -> SELECT INTO ...`), from, to, cite - and a **stop reason** per leaf: depth, fan-out cap (default 200 rows), `dynamic CALL unresolved`, `not in index`, `partial (ref-mod/subscript)`, `derived (arithmetic)`, `sort/ICETOOL step between writer and reader (bytes may be reformatted)`, `non-COBOL`.
- `field X` gets "Flows to (1 hop) / Flows from (1 hop)"; `literal` replaces `flow_from` with the same engine from every `move_to` target; `column`'s "value from / value to" (query.py:2184-2196) becomes multi-hop; `diff OLD NEW` (query.py:3281-3441) runs `flow` (depth 2) from the targets of every MOVE/COMPUTE/STRING on a changed line of the NEW copy - that is the direct answer to "I changed a MOVE, what is the business reach"; `pack --kind field` includes the rows inside the budget. Optional and cheap: JCL `step.parm` (schema.sql:407) -> the program's LINKAGE position 1, so a PARM-driven switch is a flow too.

**Tests (tests/, fixtures).** Add PGMA/PGMB/PGMC + OUTREC/INREC + JOBA/JOBC (the scratch estate reproduces the shape; ERRPGM.cbl already covers the literal route) and assert: (1) `flow PM-POLICY-STATUS --program PGMA` reaches PGMA.WS-STAT, PGMA.OUT-STATUS, `PROD.POLICY.OUT` bytes 13-14, PGMC.IN-STATUS (its test @PGMC:16), PGMB.LK-STAT, PGMB.WS-X, PGMB.DB-STAT, AUDIT_TBL.STATUS_CD; (2) `MOVE POLICY-RECORD TO WS-COPY-REC` yields the twin at offset 12 len 2; (3) a REDEFINES fixture prints the alias; (4) a subscripted / ref-modified target is `partial`; (5) MOVE CORRESPONDING pairs by name; (6) `--back` from AUDIT_TBL.STATUS_CD reaches PROD.POLICY.MASTER bytes 13-14; (7) a LINK COMMAREA fixture reaches DFHCOMMAREA; (8) an unresolved dynamic CALL prints its stop reason; (9) `diff` on a changed MOVE line prints the flow. ## Which gaps matter most for change impact

Rows 2, 5, 22, 24, 28 are one gap: **value flow by name change**. Today every impact answer is bounded by the field's own name plus REPLACING aliases and a one-hop byte twin; the moment a program does `MOVE PM-POLICY-STATUS TO WS-STAT` the estate loses the thread, and that MOVE is the normal way COBOL passes anything anywhere. It affects the three questions the user asks most - "if I change this, who is hit", "where did this bad value come from", "where does this code end up" - and it is the one gap that costs a re-parse, so it belongs at the top of the batch. Second is **time** (rows 4, 7, 42): rerun/restart and schedule-order questions are answered today by a human reading `job` output, and every incident call starts with exactly those two questions; RM-04 needs no parser change once a scheduler export is loaded, so it can follow without waiting for a night. Third is **offset to statement** (row 18): every S0C7/S0C4 triage without it is "cannot localise", and RM-01 needs one real listing to build against. Rows 9, 10, 15, 43 are smaller joins the tables already almost support (DFHCOMMAREA by name, segment <-> I/O area, card <-> SORTIN copybook, DSN <-> FD copybook) and can ride on the same batch cheaply. Everything marked full above is genuinely full within the stated caveats; the tool is strong on "what exists and who names it" and weak on "what moves and when".
